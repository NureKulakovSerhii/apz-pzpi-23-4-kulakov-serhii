3 ОПИС ВИКОНАНОЇ РОБОТИ
				
	3.1 Загальні відомості про систему
	Назва системи: Інформаційна система та вебплатформа “IMDb” (Internet Movie Database).
	Розробник: Колін Нідгем - британський інженер та розробник, який у 1990 році створив першу базу даних та пошукові скрипти для системи, а нині є генеральним директором IMDb.
	Призначення системи
- Область застосування: Глобальні індустрія розваг, медіа-аналітика, цифрова дистрибуція контенту та рекомендаційніі системи.
- Користувачі: глядачі, кінокритики, професійні учасники кіноіндустрії, а також розробники ПЗ, які використовують API системи.
- Основні функції: агрегація метаданих про фільми, серіали та персоналії; ведення користувацьких рейтингів та рецензій; персоналізований рекомендаційний двигун; пошук за багатьма критеріями; забезпечення доступу до медіа-контенту та інтеграція зі стрісінговиви платформами.
　　　　3.2 Архітектурний стиль системи 
　　　　Платформа IMDb побудована на базі подієво-орієнтованої мікросервісної архітектури. На рівні окремих сервісів застосовується шаровий стиль для ізоляції логіки. Обґрунтування вибору:
　　　　- Відмовостійкість: Збій у сервісі рекомендацій чи рецензій не заважає користувачеві переглядати основну сторінку з метаданими фільму.
　　　　- Асинхронність: Дії користувачів (наприклад, виставлення оцінок) публікуються як події в шину дних. Користувач миттєво отримує відповідь, а важкі алгоритми перерахунку рейтингів обробляють цю інформацію у фоновому режимі.
　　　　- Гнучке масштабування: Сервіси пошуку та перегляду фільмів, які отримують 90% усього трафіку (читання), масштабуються незалежно від модулів редагування чи авторизації (запис).
　　　　3.3 Основні компоненти системи
- Інтерфейс користувача (FrontEnd): Побудований на базі SPA-фрейморків (Next.js/React) із використанням серверного рендерингу (SSR) для швидкого завантаження та SEO-оптимізації. Також включає нативні мобільні застосунки для iOS та Android.
- Серверна частинв (Backend): Центральний шлюз API Gateway (на базі AWS API Gateway / Kong), який приймає запити від клієнтів, виконує автентифікацію, перевірку JWT-токенів, маршрутизацію та обмеження частоти запитів (Rate Limiting).
- Рівень бізнес-логіки (Core Services): Набір автономних мікросервісів (написаних на Java, Go та Python). Головні з них сервіс пошуку, сервіс рецензій, аналітичний модуль розрахунку рейтингів та рекомендаційний рушій.
- Рівень зберігання даних: Використовує концепцію полаглотичного збереження:
	- Amazon DynamoDB - для швидкого доступу до графів 	метаданих фільмів та акторів.
	- PostgreSQL - для профілів користувачів та білінгу IMDbPro.
	- Elasticsearch - для повнотекстового пошуку.
- Допоміжні сервіси: інфраструктурні модулі для забезпечення життєздатності сиситеми: брокер повідомлень (Apache Kafka), система кешування (Redis/Memcached), логування (ELK Stack) та моніторинг (Prometheus + Grafana).
	3.4 Взіємодія компонентів
- Потоки даних: Зовнішні запити від користувачів спрямовуються через браузери та мобільні застосунки до єдиної точки входу (шлюзу). Шлюз розподіляє запити між сервісом профілів та сервісом метаданих фільмів. Після цього дані про активність користувачів асинхронно транслюються в брокер повідомлень для аналітики.
- ПРотоколи взаємодії: Зовнішня комунікація “клієнт-сервер” виконується за протоколами HTTPS (REST/GraphQL). Внутрішня міжсервісна взаємодія реалізована за допомогою високопродуктивного бінарного протоколу gRPC (для синхроних запитів) та протоколу AMQP/Kafka-native (для асинхроних подій).
- Механізми синхронізації: Синхронізація даних між реляційною БД користувачів та NoSQL сховищем метаданих відбувається за принципом відкладеної узгодженості через брокер повідомлень. Для детального аналізу статичної структури підсистеми обробки контенту було побудовано діаграму класів (див. Рисунок 3.1)

Рисунок 3.1 - UML-діаграма класів
	Аналітичний опис діаграми класів:
- Інтерфейс ISentimentAnalyzer виступає в ролі абстрактного базису, який декларує єдиний контракт та сигнатуру методу AnalyzeReviewAsync(string reviewText) для всіх можливих модулів аналітики.
- Клас BedrockSentimentAnalyzar реалізує цей інтерфейс і повністю інкапсулює в собі логіку формування запитів та взаємодії із зовнішнім хмарним сервісов ШІ (AWS Bedrock API), забезпеуючи виконання принципу єдиної відповідальності (SRP).
- Компонент бізнес логіки (ReviewService) не залежить від конкретної реалізації аналізатора і працює з ним виключно через інтерфейсну залежність. Це дозволяє дотримуватися принципу інверсії залежностей (DIP) і за потреби легко підмінити ШІ-сервіс на будь-яку іншу локальну чи хмарну модель без модифікації ядра системи. Для моделювання процесу передачі керування між об’єктами в часі, демонстрації делегування запитів та безпосереднього асинхроного механізму обробки даних під час виконання транзакції було побудовано діаграму послідовності (див. Рисунок 3.2)

Рисунок 3.2 - UML-діаграма послідовності
	Аналітичний опис діаграми послідовності:
- Ініціація запиту: Процес розпочинається на рівні користувача, який через веб-інтерфейс надсилає HTTP POST запит із текстом рецензії. API Gateway виступає єдиною точкою входу, автентифікує користувача та маршрутизує виклик у внутрішню мережу через gRPC-протокол до мікросервісу ReviewService.
- Делегування обробки: Отримавши запит, ReviewService не виконує аналіз самостійно, а делегує задачу визначення емоційного забарвлення тексту методу AnalyzeReviewAsync, який підтримується інтерфейсною залежністю.
- Зовнішня інтеграція та синхронізація: Об’єкт BedrockSentimentAnalyzer транслює сформований запит через захищене HTTPS-з’єднання до хмарного AWS Bedrock API. Після отримання відповіді у форматі JSON, об’єкт повертає текстовий вердикт назад у сервіс. ReviewService асинхронно зберігає оновлені дані в базу даних та повертає статус 200 ОК клієнту, забезпечуючи ізольовану та швидку зміну стану інтерфейсу без блокування потоків.
	3.5 Масштабованність та надійність
- Механізми балансування навантаження: Використовується дволінійне балансування. На глобальному рівні геграфічний балансувальник (AWS Route 53) розподіляє трафік між найближчими дата-центрами. На рівні інфраструктури хмарні балансувальники рівномірно розподіляють HTTP/gPRC запити між активними подами у кластері.
- Відмовостійкість: Реалізовано патер Circuit Breaker (автоматичний вимикач). Якщо мікросервіс рецензій або рекомендацій зазнає збою запити до нього ізолюються. Платформа продовжує працювати, просто тимчасово приховуючи цей блок від користувача та запобігаючи каскадному падінню всієї системи.
- Кешування: Застосовується розподілений кеш у пам’яті на базі Redis для зберігання “гарячих даних” (сесі користувачів, топ-250 фільмів, популярні актори). Для статичного контенту (постери, кадри з фільмів, відео) розгорнуто мережу доставки контенту CDN.
- Реплікація: Бази даних налаштовані в режимі Multi-AZ із розподілом ролей. Головна нода (Master) приймає операції запису, а дані синхронно реплікуються на кілька нод для читання (Read Replicas), що розвантажує основну БД під час масових пошукових запитів.
- Контейнеризація та хмарна інфраструктура: Усі мікросервіси повністю контейнеризовані за допомогою Docker та працюють під керуванням оркестратора Kubernetes. Налаштовано автоматичне горизонтальне масштабування, яке додає або видаляє контейнери залжено від поточного рівня навантаження на процесор чи мережу.
	3.6 Приклади програмної реалізації
	Для автоматичного аналізу тональності тисяч нових рецензій, що надходять на IMDb щохвилини, архітектура системи передбачає інтеграцію з мовними моделями штучного інтелекту через хмарне API AWS Bedrock. У Додатку В наведно фрагмент програмного коду інтеграційного сервісу мовою C#.
