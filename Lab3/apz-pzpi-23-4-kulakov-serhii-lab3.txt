2 ЗАВДАННЯ

　　　　На цій лабораторній роботі потрібно розробити front-end частину програмної системи. Ця частина системи повинна підтримувати роботу клієнтів у веб-режимі та забезпечувати адміністрування системи, тобто мати окремий інтерфейс для звичайних користувачів і окремий — для адміністраторів (відповідно до ролей користувачів вашої системи). Користувацький інтерфейс та інтерфейс адміністрування повинні підтримувати інтернаціоналізацію та локалізацію, а саме, забезпечувати: підтримку української на англійської мов сайту, формат дати та часу відповідний регіону, порядок сортування текстових значень, різні напрями введення тексту тощо. Адміністрування системи повинно забезпечувати: управління користувачами системи, управління даними системи, створення резервних копій налаштувань та даних, експорт та імпорт даних та налаштувань.


3 ОПИС ВИКОНАНОЇ РОБОТИ

	3.1 Вступ та опис прийнятих інженерних рішень
	У межах лабораторної роботи було розроблено веб-застосунок для оренди складських приміщень, який інтегрується в загальну екосистему “Програмна система для оренди малих складських приміщень”. Застосунок призначений для швидкого пошуку, перегляду та публікацїї оголошень про оренду комерційних складів, а також для адміністрування системи. Прийняті інженерні рішення:
	- Платформа та бібліотеки: React 18 для побудови компонентного, декларативного UI, React Router v6 для маршрутизації, Vite для швидкої збірки проекту.
	- Архітектура застосунку: Компонентна архітектура з використанням React Hooks (useState, useEffect, useContext). Застосунок побудовано за принципом розділення відповідальності: окремі сервіси для роботи з API, окремі компоненти для відображення, контексти для глобального стану.
	- Мережева взаємодія: Fetch API для асинхронних HTTP-запитів до RESTful API бекенду. Авторизація реалізована на базі протоколу JWT (JSON Web Token) зі зберіганням токену у localStorage. Створення оголошень з медіа-файлами реалізовано через передачу даних у форматі multipart/form-data.
	- Керування станом: Для глобального стану використовуються контексти (ThemeContext, LanguageContext, RegionContext). Локальний стан компонентів керується через хуки useState. Стан завантаження та помилок обробляється на рівні кожного компонента.
	- Інтернаціоналізація: Реалізовано підтримку двох мов (українська та англійська) через кастомний хук useTranslation, який надає доступ до об’єкта перекладів. Всі текстові рядки винесені у файли локалізації en.js та uk.js.
	3.2 Архітектура та взаємодія з іншими частинами системи
	Веб-застосунок виступає як клієнтська частина системи. Основна бізнес-логіка, збереження даних у СКБД (MS SQL Server) та обробка зображень (Cloudinary) відбуваються на стороні серверного API (ASP.NET Core). Клієнт взаємодіє з сервером через захищене REST API, передаючи JWT-токен у заголовку Authorization: Bearer для ідентифікації сесії користувачів. Взаємодія компонентів всередині застосунку:
	- Header: Навігаційний компонент, який перевіряє статус автентифікації та роль користувача, динамічно відображаючи відповідні пункти меню (включаючи адмін-панель для модераторів).
	- AppContext: Надає глобальний стан теми, мови, часового поясу та формату дати для всіх компонентів через хуки useTheme, useLanguage, useRegion.
	- Сервіси: Інкапсулюють логіку HTTP-запитів до бекенду (advertService, profileService, supportService, adminUserService, statisticsService).
	- Маршрутизація: Захищені маршрути (PrivateRoute) перевіряють наявність валідного JWT-токену перед доступом до персоналізованих сторінок. Рольовий доступ реалізовано через перевірку ролі Moderator у JWT-токені.
	3.3 UML-діаграми
	3.3.1 UML Діаграма прецедентів
	Діаграма описує поведінку системи з точки зору трьох ролей: Неавторизованого користувача (Гість), Авторизованого користувача та Модератора (Додаток Б.1).
	Опис діаграми прецедентів:
	Ця діаграма чітко розмежовує права доступу всередині веб-застосунку. Система оперує трьома основними акторами:
	- Гість (Неавторизований користувач): Має базовий рівень доступу до ознайомчого контенту. Він може вільно переглядати стрічку оголошень на головній сторінці та виконувати пошук складів із застосуванням фільтрів. Для переходу до дій, що змінюють стан системи (додавання в обране, публікація оголошення), він обов’язково має пройти прецеденти авторизації або реєстрації.
	- Авторизований користувач: Володіє повним спектром прав для роботи з особистими даними. Він успадковує можливості перегляду, але додатково може взаємодіяти з персоналізованими розділами додатка (профіль, обрані оголошення, порівняння, чат підтримки), а також створювати, редагувати та видаляти власні оголошення.
	- Модератор: Має всі права авторизованого користувача та додатково отримує доступ до адміністративної панелі. Він може активувати або видаляти оголошення, блокувати або розблоковувати користувачів, переглядати статистику платформи та експортувати дані.
	- Зв’язки <<include>>: Прецедент “Створення оголошення” обов’язково включає в себе завантаження графічного медіа-файлу. Крім того, якщо операція ініціюється гостем, система примусово викликає прецедент “Авторизація”, реалізуючи бізнес-правило захисту ендпоїнтів. Всі дії, що потребують автентифікації (створення, редагування, видалення оголошення, додавання до обраних, порівняння, робота з чатом та тікетами) мають зв’язок <<include>> з прецедентом “Авторизація”.
	3.3.2 UML Діаграма компонент
	Діаграма компонент (Component Diagram) демонструє модульну архітектуру веб-застосунку, внутрішні зв’язки між його шарами за принципом компонентного підходу, а також спосіб інтеграції з сервером (Додаток Б.2)
	Опис діаграми компонент:
	Діаграма відображає низьку зв’язність та високу зв’язаність проектованого програмного забезпечення:
	- UI Components: Шар представлення, написаний на React з використанням JSX, є суто декларативним. Він не містить бізнес-логіки та лише відображає дані, отримані з хуків та контекстів, а також передає події користувача до відповідних обробників.
	- Pages: Компоненти-сторінки, що комбінують UI-компоненти для формування закінчених екранів застосунку (головна сторінка, профіль, пошук, адмін-панель тощо). Кожна сторінка використовує хуки для доступу до стану та сервісів.
	- Hooks: Кастомні React-хуки (useTranslation, useTheme, useLanguage, useRegion), які інкапсулюють логіку доступу до глобального стану та перекладів. Вони забезпечують чистий та перевикористовуваний спосіб отримання даних з контекстів.
	- Contexts: Шар глобального стану, реалізований через React Context API. Включає ThemeContext (керування темою), LanguageContext (керування мовою) та RegionContext (керування часовим поясом та форматом дати). Контексти зберігають значення в localStorage для відновлення після перезавантаження сторінки.
	- Services: Шар абстракції даних, що містить функції для виконання HTTP-запитів до бекенду (advertService, profileService, supportService, adminUserService, statisticService). Кожен сервіс інкапсулює логіку формування запитів, додавання заголовків авторизації та обробки відповідей.
	- Router: Шар маршрутизації на основі React Router v6. Визначає відповідність URL-адрес компонентам-сторінкам, реалізує захист маршрутів через PrivateRoute та перевірку ролей для доступу до адміністративних розділів.
	- Взаємодія з бекендом: Зв’язок між компонентом Services та зовнішньою системоюASP.NET Core Web API здійснюється за допомогою захищеного протоколу HTTPS через стандартні REST-запити (GET, POST, PUT, DELETE) та передачу даних у форматах JSON та multupart/form-data для файлів. Авторизація запитів відбувається шляхом додавання JWT-токену до заголовка Authorization Bearer.
	3.3.3 UML Діаграма діяльності
	Діаграма діяльності (Activity Diagram) детально моделює алгоритм поведінки додатка при спробі створити нове оголошення, враховуючи розгалуження логіки авторизації, клієнтську валідацію та мережеву взаємодію з сервером (Додаток Б.3)
	Опис діаграми діяльності:
	Дана діаграма ілюструє повний цикл створення оголошення користувачем, починаючи від ініціації дії і закінчуючи отриманням результату.
	- Перевірка авторизації: На початку роботи система перевіряє наявність дійсного JWT-токену в локальному сховищі браузера. Якщо користувач не авторизований, відбувається перенаправлення на сторінку входу. Після успішної автентифікації токен зберігається, і користувач повертається до процесу створення оголошення.
	- Введення даних: Користувач заповнює форму, яка включає текстові поля (заголовок, опис, адреса), числові поля (ціна, площа, поверх), випадаючі списки (тип будівлі, місто) та групи чекбоксів (комунікації, побутова техніка, інфраструктура). Також передбачено завантаження фотографій з попереднім переглядом.
	- Валідація та відправка: Після заповнення форми виконується перевірка обов’язкових полів. У разі виявлення помилок користувач отримує відповідне повідомлення. Якщо всі дані коректні, активується стан завантаження, форма блокується для запобігання повторним відправкам, а дані конвертуються у формат multipart/form-data  для передачі на сервер.
	- Завершення операції: При успішному створенні оголошення форма очищується, а користувач перенаправляється на сторінку профілю для перегляду опублікованого оголошення. У разі помилки (проблеми з мережею, помилка валідації на сервері тощо) користувач бачить пояснювальне повідомлення, а форма розблоковується для виправлення даних.
	3.3.4 UML Діаграма станів
	Діаграма станів описує життєвий цикл стану автентифікації користувача в застосунку, включаючи зміни при вході, виході, реєстрації, закінченні терміну дії токену, а також блокуванні та розблокуванні облікового запису модератором (Додаток Б.4)
	Опис діаграми станів:
	Дана діаграма описує можливі стани системи щодо автентифікації користувача та умови переходу між цими станами.
	- Стан “Неавторизований”: Це початковий стан системи, в якому перебуває будь-який відвідувач при першому відкритті застосунку. У цьому стані користувач має доступ лише до загальнодоступних сторінок (головна, пошук, реєстрація, логін). Перехід до наступного стану можливий при успішному виконанні операцій логіну або реєстрації. Вихід із стану можливий при закритті сторінки.
	- Стан “Авторизований”: Цей стан настає після успішної верифікації облікових даних користувача. JWT-токен зберігається в локальному сховищі та використовується для авторизації всіх наступних запитів. Користувач отримує доступ до персоналізованих розділів (профіль, обрані, порівняння, чат підтримки). Повернення до попереднього стану відбувається при добровільному виході з облікового запису або автоматично при закінченні терміну дії токену.
	- Вкладені стани “Користувач” та “Модератор”: Всередині авторизованого стану виділяються дві підстани, які визначають набір доступних функцій. У стані “Користувач” доступна лише базова функціональність платформи. Перехід до стану “Модератор” відбувається при призначенні відповідної ролі адміністратором, після чого користувач отримує доступ до адміністративної панелі з можливістю активації оголошень, блокування користувачів, перегляду статистики та експорту даних.
	- Стан “Заблокований”: Цей стан є особливим випадком авторизованого стану, в який користувач може бути переведений модератором. При блокуванні всі активні оголошення користувача автоматично деактивуються, а сам користувач втрачає можливість створювати нові оголошення та залишати повідомлення в чатах. Розблокування виконується також модератором і повертає користувача до стандартного авторизованого стану з автоматичною реактивацією всіх його оголошень.
	3.4 Опис реалізації компонентів та функціоналу
	У даному розділі наведено короткий опис програмної реалізації ключових модулів веб-застосунку системи оренди складських приміщень.
	- Логіка маршрутизації та навігації: Головний компонент App містить Router з BrowseRouter. Компонент PrivateRoute перевіряє наявність JWT-токену перед доступом до захищених сторінок. Для модераторів додатково відображаються маршрути адміністративної панелі та відповідний пункт у хедері.
	- Управління глобальним станом: Тема оформлення, мова та регіональні налаштування (часовий пояс, формат дати) реалізовані через React Context. Усі налаштування зберігаються в localStorage для відновлення після перезавантаження сторінки.
	- Обробка форми створення оголошення: Для поодиноких значень (тип будівлі, місто) використано випадаючі списки. Для множинних значень (комунікації, техніка, інфраструктура) реалізовано групи чекбоксів. Перед відправкою виконується клієнтська валідація обов’язкових полів. 
	- Завантаження даних через multipart/form-data: При створенні оголошення текстові значення конвертуються у числові ідентифікатори за допомогою динамічних мапів, які автоматично перебудовуються при зміні мови. Фотографії додаються до FormData та передаються на сервер у складі multipart-запиту.
	- Система чатів підтримки: Чат оновлюється кожні 5 секунд. При надісланні повідомлення форма очищується, а скрол автоматично прокручується до останнього повідомлення. Модератори можуть призначати тікети собі та закривати їх після вирішення проблеми.
	- Адміністративна панель: Сторінка управління користувачів містить таблицю з фільтрацією за статусом та пошуком. При блокуванні користувача всі його оголошення автоматично деактивуються, при розблокуванні - реактивуються. Статус візуально виділяється кольоровим бейджем.
4 ВИСНОВКИ

	У ході виконання лабораторної роботи було розроблено веб-застосунок для оренди малих складських приміщень. Реалізовано основні функціональні модулі: перегляд та пошук оголошень з фільтрацією, створення та редагування оголошень, додавання до обраних, порівняння складів, чат підтримки, адміністративну панель для модерації контенту та управління користувачами інтернаціоналізацію та локалізацію, підтримку зміни формату дати та часу відповідний до регіону, експорт та імпорт даних.
