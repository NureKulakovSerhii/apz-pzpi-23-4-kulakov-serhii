2 ЗАВДАННЯ

　　　　На цій лабораторній роботі потрібно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ, вказані лектором, а саме Kotlin для Android та Swift для iOS. Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи.


3 ОПИС ВИКОНАНОЇ РОБОТИ
　　　　
　　　　3.1 Вступ та опис прийнятих інженерних рішень
　　　　У межах лабораторної роботи було розроблено мобільний клієнтський застосунок для платформи Android, який інтегрується в зашальну екосистему  “Програмна система для оренди малих складських приміщень”. Застосунок призначений для швидкого пошуку, перегляду та публікації оголошень про оренду комерційних складів. Прийняті інженерні рішення:
　　　　- Платформа та мова: Kotlin та фреймворк Jatpack Compose для побудови сучасного, декларативного, реактивного UI без використання застарілих XML-view.
　　　　- Архітектура застосунку: MVVM (Model-View-ViewModel). Вона забезпечує чітке розподілення бізнес-логіки та UI-компонентів, спрощує тествування та масштабування додатка.
　　　　- Мережева взаємодія: Бібліотека Retrofit 2 для асинхронних HTTP-запитів до RESTful API бекенду. Авторизація реалізована на базі протоколу JWT (JSON Web Token). Створення оголошень з медіа-фійлами реалізовано через передачу потокових даних формату multipart/form-data.
　　　　- Керування станом: Стан екранів та форми створення оголошень контролюється за допомогою інструментів реактивного стану Jetpack Compose (mutableStateOf, mutableStateListOf, collectAsState).
　　　　3.2 Архітектура та взаємодія з іншими частинами системи
　　　　Мобільний застосунок виступає як тонкий клієнт. Основна бізнес-логіка, збереження даних у СКБД (MS SQL Server) та обробка зображень (Cloudinary) відбуваються на стороні серверного API (ASP.NET Core). Клієнт взаємодіє з сервером через захищене REST API, передаючи JWT-токен у заголовку Authorization: Bearer <token> для ідентифікації сесії користувача.
　　　　3.3 UML-діаграми
　　　　3.3.1 UML Діаграма прецедентів
　　　　Діаграма описує поведінку системи з точки зору двох ролей: Неавторизованого користувача (Гість) та Авторизованого користувача (Додаток Б.1)
　　　　Опис діаграми прецедентів:
　　　　Ця діаграма чітко розмежовує права доступу всередині мобільного клієнта. Система оперує двома основними акторами:
　　　　- Гість (Неавторизований користувач): має базовий рівень доступу до ознайомчого контенту. Він може вільно переглядати стрічку оголошень на головному екрані та виконувати пошук складів із застосуванням фільтрів. Для переходу до дій, що змінюють тан системи (додання в обране, публікація), він обов’язково має пройти прецеденти авторизації або реєстрації.
　　　　- Авторизований користувач: володіє певним спектром прав. Він успадковує можливості перегляду, але додатково може взаємодіяти з персоналізованими секціями додатка (Профіль, Обране).
　　　　- Зв’язки <<include>>: Прецедент “Створення нового оголошення” обов’язково включає в себе завантаження графічного медіа-файлу (UC_Upload). Крім того, якщо операція ініціюється гостем, система примусово викликає прецедент “Авторизація/Логін”, реалізуючи бізнес-правило захисту ендпоїнтів.
　　　　3.3.2 UML Діаграма компонент
　　　　Діаграма компонент (Component Diagram) демонструє модульну архітектуру мобільного додатка, внутрішні зв’язки між його шарми за паттерном MVVM, а також спосіб інтеграції з сервером (Додаток Б.2)
　　　　Опис діаграми компонент:
	Діаграма відображає низьку зв’язність (Low Coupling) та високу зв’язаність (High Cohesion) проектованого програмного забезпечення:
	- UI Components: Шар представлення, написаний на Jetpack Compose, є суто декларативним. Він не містить бізнес-логіки та лише підписується на потоки станів, що надає шар в’юмоделей.
	- ViewModels: Виступає архітектурним містком. В’.моделі трансформують сирі дані з репозиторію у реактивні стани системи.
	- Domain Models & Enums: Загальний шар сутностей, куди входять переліки (City, BuildingType тощо). Він є повністю незалежним.
	- Repository & Network: Шари абстракції даних. Репозиторій приховує прямі виклики мережі, а Retrofit API Client відповідає за безпосередній транспорт даних.
	- Взаємодія з бекендом: Зв’язок між компонентом Network та зовнішньою системою ASP.NET Core Web API здійснюється за допомогою захищеного протоколу HTTPS через стандартні REST-запити та бінарні Multipart-потоки для файлів.
	3.3.3 UML Діаграма діяльності
	Діаграма діяльності (Activity Diagram) детально моделює алгоритс поведінки додатка при спробі створити нове оголошення, враховуючи розгалуження логіки авторизаці (Додаток Б.3)
　　　　Опис діаграми діяльності: 
　　　　Даний бізнес-процес демонструє механіхм “безшовного” користувацького досвіду та серверної валідації:
　　　　- Умовне розгалуження авторизації: При ініціалізації створення оголошення додаток перевіряє наявніть локально збереженого JWT-токена. Якщо його немає, дія користувача не переривається скиданням, а тимчасово делегується екрану логіну. При успішному збігу облікових даних токен оновлюється, і система автоматично повертає його на крок створення.
　　　　- Збір та підготовка даних: Користувач взаємодіє з текстовими інпутами та випадаючими меню. Окремою гілкою йде робота з системними ActivityResultLuancher для безпечного отримання локального Uri зображення.
　　　　- Клієнтська валідація та Multipart-транспорт: Перед відправкою перевіряється заповненість обов’язкових полів (назва, опис, адреса, ціна). Якщо умови виконано, додаток конвертує текстові рядки та масиви обраних чекбоксів енамів у сирі бінарні об’єкти RequestBody, пакує їх разом із файлом картинки у форму типу MultipartFormData і робить асинхроний виклик до API.
　　　　- Фіналізація: При отриманні статус-коду 200/210, стан форми скидається в Idle для запобігання дублікатів запитів, а навігатор повертає користувача на головну сторінку для перегляду оновленої стрічки.
　　　　Діаграма станів описує життєвий цикл екрана створення оголошення та зміну реактивного стану CreateAdvertState в процесі взаємодії з користувачем та віддаленим сервером (Додаток Б.4)
　　　　Опис діаграми станів:
　　　　Керування станом екрана побудовано на базі кінцевого автомату, реалізованого через sealed interface CreateAdvertState. Це гарантує, що додаток не може перебувати у двох невизначених станах одночасно:
　　　　- Стан Idle (Вільний): Початковий стан форми. Компонент відображає чисті поля для введення. Всередині цього стану відбуваються мікро-переходи введення даних: заповнення текстових полів користувачем, оновлення динамічного списку mutableStateListOf при кліках на чекбокси, а також мутація імені вибраного файлу.
　　　　- Стан Loading (Завантаження): Тригериться при натисканні на кнопку публікації. У цей моент UI блокує всі поля форми (enabled = !isLoading), приховуючи кнопку сабміту, та відображає індикатор CircularProgressIndicator. Це захищає систему від повторних натискань та дублювання сутностей у базі даних під час тривалого мережевого запиту.
　　　　- Стан Error (Помилка): Якщо під час запиту виникає виняток (відсутній інтернет) або сервер повертає помилку валідації (наприклад 400 Bad Request),автомат переходить у стан Error. Блокування знімається, а на екран виводиться червоний текст помилки. КОристувач може виправити дані, що повертає систему в Idle.
　　　　- Стан Success (Успіх): Кінціевий успішний стан, який сигналізує про завершення операції. Він викликає тригер resetForm(), очищує кеш вибраних фотографій і через зворотний виклик onAdvertCreated здійснює навігаційний перехід.
　　　　3.4 Опис реалізації компонентів та функціоналу
　　　　У даному розділі наведено детальний опис програмної реалізації ключових модулів мобільного застосунку системи оренди складських приміщень, механімів управління станом екранів, а також особливостей архітектури інтеграції з віддаленим сервером.
　　　　Логіка Навігації: Головний екран MainScreen містить загальний Scaffold із верхнім меню MainHeader. Завдяки реактивному стейту currentScreen з AuthViewModel, додаток динамічно перемикає внутрішній контент-бокс без перезавантаження активності.
　　　　Обробка Форми Створення: Екран CreateAdvertScreen динамічно інтегрує списки переліків (Enums) нашої доменної моделі. Для поодиноких значень (City, BuildingType) використано Material 3 компоненти ExposedDropdownMenuBox. Для масивів (Communications, HouseholdAppliances, Infrastructure) реалізовано список інтерактивних рядків з CheckBox.
　　　　Завантаження Медіа та Списків через Multipart: Оскільки бекенд очікує складні модель CreateAdevrtDto, яка містить як текстові поля, так і файл зображення з колекціями числових ідентифікаторів енамів, у CreateAdvertViewModel реалізовано мапінг даних у плоскі об’єкти RequestBody та масиви індексованих MultipartBody.Part із дублюванням однакових ключів полів для коректної десеріалізації на стороні ASP.NET Core API.
