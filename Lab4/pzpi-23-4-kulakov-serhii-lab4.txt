2 ЗАВДАННЯ

　　　　В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: - масштабувати сервер горизонтально — багато копій сервера виконують однакові функції для різних користувачів; - масштабувати сервер вертикально — різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. З технічної точки зору, масштабування можна виконати так: - деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; - деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. - ваш власний спосіб показати що система може масштабуватись. На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система.


3 ОПИС ВИКОНАНОЇ РОБОТИ
　　　　
　　　　3.1 Опис стратегії масштабування системи
　　　　У межах виконання лабораторної роботи для забезпечення високої доступності, відмовостійкості та здатності обробляти велику кількість одночасних запитів до веб-системи “Програмна система для оренди малих складських приміщень” було обрано стратегію горизонтального масштабування.
　　　　Суть та обґрунтування вибору стратегії:
　　　　На відміну від вертикального масштабування (яке передбачає нарощування потужності одного сервера: додавання CPU, RAM тощо), горизонтальне масштабування полягає у збільшенні кількості ідентичних екземплярів (реплік) застосунку, які працюють паралельно і ділять між собою вхідний трафік. Вибір цієї стратегії обґрунтований такими факторами:
　　　　- Еластичність та гнучкість: Кількість реплік бекенду можна динамічно збільшувати під час пікових навантажень (наприклад, акцій чи напливу користувачів) і зменшувати в періоди затишшя для економії ресурсів.
　　　　- Економічна ефективність: Набагато дешевше запустити кілька стандартних або слабких серверів (інстансів), ніж купувати один супер-комп’ютер.
　　　　- Забезпечення високої доступності: Якщо один із п’яти запущених серверів бекенду вийде з ладу через критичну помилку або апаратний збій, система продовжить роботу. Балансувальник просто перестане надсилати туди трафік і перенаправить його на чотири інші робочі репліки. Користувачі навіть не помітять збою. 
　　　　У межах цієї лабораторної роботи було реалізовано архітектуру, що складається з трьох основних рівнів:
　　　　- Клієнтський рівень: Інструмент Locust, який імітує масові синхронні запити від великої кількості користувачів (150 віртуальних юзерів).
　　　　- Рівень балансування: Веб-сервер Nginx, який виступає єдиною точкою входу для всіх запитів (на порту 9000), приймає їх і розподіляє між серверами.
　　　　- Обчислювальний рівень: П’ять незалежних екземплярів ASP.NET Core Web API (запущених на локальних портах 5001, 5002, 5003, 5004, 5005) які підключені до бази даних MS SQL Server.
　　　　Для розподілу запитів у межах горизонтального масштабування було використано базовий алгоритм Round Robin, за якого кожен новий запит від Nginx послідовно відправляється на наступний за списком сервер: перший запит - на 5001, другий на 5002 і так далі до 5005, після чого цикл повторюється.
　　　　3.2 Опис технічних рішень, які роблять масштабування можливим
　　　　Горизонтальне масштабування системи реалізовано завдяки трьом ключовим технічним рішенням:
　　　　- Stateless-архітектура: Бекенд спроектовано за принципом Stateless. Екземпляри застосунку не зберігають сесії чи стани користувачів у своїй оперативній пам’яті.
　　　　- Балансування трафіку через Nginx: Веб-сервер Nginx виступає як Reverse Proxy та єдина точка входу на порту 9000. У файлі nginx.conf налаштовано блок upstream, який об’єднує 5 реплік API у спільний пул. Запити розділяються за алгоритмом Round Robin. 
　　　　- Асинхронний веб-сервер Kestrel: Репліки API запускаються у фонових терміналах через вбудований кросплатформений сервер Kestrel командою dotnet run --urls. Завдяки повній асинхронності обробки запитів в .NET 8, сервери мінімізують блокування потоків процесора під час очікування відповідей від СУБД.
　　　　3.3 Аналіз вузьких місць системи
　　　　На основі навантажувальних тестів було виявлено технічні обмеження, де ресурси системи вичерпуються першими під впливом інтенсивного трафіку:
　　　　- Пул з’єднань та пропускна здатність централізованої СУБД (MS SQL Server): Головне вузьке місце всієї системи. Навіть при роботі 5 реплік API, максимальний час відповіді зафіксувався на позначці 2604 мс через жорстку конкуренцію за вільні підключення в пулі з’єднань EF Core та ліміт швидкості дискової підсистеми СУБД при виконанні важких вибірок для методу /all-adverts.
　　　　- Ресурси CPU та RAM при ефекті “холодного старту” (.NET Core): Початковий стрибок затримки до 2500-4100 мс зумовлений тим, що в перші 15 секунд тесту ресурси процесора та пам’яті сервера активно вичерпуються на JIT-компіляцію методів .NET 8, первинну ініціалізацію контексту AppDbContext та компіляцію LINQ-запитів у SQL-код.
　　　　- Потоки обробки Kestrel-сервера в одиночній конфігурації: При тестуванні лише одного екземпляру API критичним лімітом стають доступні робочі потоки та черга HTTP-запитів. Без масштабування наплив 150 користувачів викликає лавиноподібне накопичення запитів у черзі, що збільшує максимальний час відповіді до 6078 мс. 
　　　　3.4 Опис навантажувальних тестів та ілюстрація зв’язку з масштабуванням
　　　　Для перевірки роботи системи було проведено два тести в інструменті Locust. Умови в обох випадках були однаковими: 150 віртуальних користувачів запускалися поступово (по 10 на секунду) і одночасно викликали ендпоїнт GET /api/Advert/all-adverts через балансувальник Nginx.
　　　　Перший тест показує, як система поводиться в базовому режимі, коли працює лише один екземпляр веб-сервера API. Під час напливу користувачів один сервер Kestrel почав сильно гальмувати: час відповіді для 95% запитів підскочив до 4100 мс, а найдовший запит оброблявся аж 6078 мс. Це сталося через те, що запити накопичувалися в черзі, яку один сервер не встигав розгрібати. Результати цього експерименту наведено на рисунках Б.1 та Б.2 додатка Б.
　　　　Другий тест показує роботу системи після горизонтального масштабування, коли Nginx почав ділити трафік між 5 паралельними репліками API. Завдяки розподілу навантаження максимальна затримка в момент запуску користувачів упала більш ніж удвічі - до 2604 мс. Після цього час відповіді миттєво впав до 5-18 мс і залишався стабільним до кінця тесту. Загальний середній час обробки запитів знизився на 26%. Результати цього експерименту наведено на рисунках Б.3 і Б.4 додатка Б.
　　　　Отримані метрики чітко доводять: чим більше реплік застосунку ми запускаємо, тим стабільніше система тримає велике навантаження і тим швидше користувачі отримують відповідь. Порівняльні дані обох тестів наведено в таблиці 3.1

4 ВИСНОВКИ
　　　　
　　　　У результаті лабораторної роботи було успішно реалізовано горизонтальне масштабування веб-API за допомогою балансувальника Nginx. Навантажувальне тестування в Locust довело ефективність рішення: при 150 одночасних користувачах середній час відповіді знизився на 26%, а максимальна затримка впала в 2.3 рази при 0% помилок і стабільній швидкості. Головними вузькими місцями системи залишилися ефект “холодного старту” .NET 8 на початку тесту та обмеження пропускної здатності спільної бази даних MS SQL Server.
